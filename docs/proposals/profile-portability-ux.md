# Profile Backup / Restore / Transfer UX

**Status: UX accepted by Human in PR #881; runtime implementation tracked in #882.** Issue [#76](https://github.com/BotHarness/BotHarness/issues/76), 2026-10-05. [中文](profile-portability-ux.zh.md).

This proposal translates accepted [ADR-0041](../adr/0041-one-database-owns-botharness-operational-state.md), [ADR-0042](../adr/0042-profile-backup-coordinates-database-files-and-dsh-sessions.md), [ADR-0043](../adr/0043-profile-transfer-prevents-identity-split-brain.md) and [ADR-0044](../adr/0044-restore-revalidates-target-runtime-dependencies.md) into a minimal interaction. Product terms remain owned by [CONTEXT](../../CONTEXT.md); the [living architecture](../architecture/botharness-architecture.md) remains the integrated authority. This document is a review artifact, not a published user guide or a second architecture authority.

## Entry and information hierarchy

Add **Profile data** to **Settings → Bot mode**. Its top level has two actions: **Export Profile** and **Import Profile**. Copy: “A Profile backup preserves every Bot’s identity and history. To share a Bot as a new identity, use PersonaBot Export.” PersonaBot sharing/publishing remains [#17](https://github.com/BotHarness/BotHarness/issues/17) / [#18](https://github.com/BotHarness/BotHarness/issues/18); no publisher or per-Bot selector appears here.

The export dialog orders content as: purpose → included data and estimated size → optional Session history → destination → confirmation. Import orders it as: selected file and validation → target → identity/activation warning → confirmation → restore progress → readiness. Use the native modal, form, progress and alert primitives with DSH tokens. A wide, scrollable dialog shows summary and details in one column; narrow windows retain the same order. Keep status, cancellation and primary action visible; keyboard focus enters the dialog and returns to the invoking action. Errors use destructive tokens; omitted or unavailable content uses an informational warning, not an error.

The Client Settings Slot exists in `packages/client/src/client/index.ts`: `settings.section` / `botharness` contains the application-defined `botharness.settings.item` list. A future `profile-data` registration uses that list and the existing Host↔Client API Gateway seam; it does not install another `/api` interceptor. These are verified current entry seams, not existing backup endpoints. All portability operations below are proposed application-defined Host operations. DSH owns Profile composition and Session Persistence; importing does not copy its private persistence backend or invent a DSH Profile-management API.

## Export one file

1. **Export Profile** opens the complete core summary: Bot count, full operational database, all Soul/Memory files, reachable Attachments, dependency manifest and purge checkpoint. No core checkbox or per-Bot selection. Name sensitive core records in the preview: message/Source Event content and revisions, non-secret account descriptors, authorization/Service Grant/Trigger records, Outbox and audit history. Deselecting DSH Session history does not exclude those records. Provider credentials, executable Plugins and Workspace contents are excluded. Show Model Presets and independent Model Plans as part of the core, never as a separate export workaround ([#505](https://github.com/BotHarness/BotHarness/issues/505)).
2. Show **Include DSH Session history** checked only when the active Session Persistence adapter supports portable export/import. Show referenced Session count, estimated bytes and “Session history can contain private conversations and tool results.” If unsupported, disable the option and say “Session content cannot be included by this persistence adapter. Ownership and historical attribution will remain, but these Sessions cannot resume.” Explicit deselection uses the same unavailable-content explanation.
3. Show estimated uncompressed content size and available destination space; explain that compressed file size becomes known on completion. Unknown estimates are labelled unknown, not zero. Final Host preflight includes staging/workspace requirements and refuses insufficient space. Choose a Human-authorized destination for one `.botharness-backup`; v1 refuses an existing destination filename and offers another name, preserving the old file.
4. Confirmation: “Create one backup file. It contains private operational data. Credentials are excluded. An older file only knows deletions made before its checkpoint.” Action **Export**; cancellation is available before atomic publication.
5. Progress phases: **Preparing snapshot → Packaging → Verifying → Saved**. A short Backup Barrier fixes database, file versions, CAS closure and selected Session cursors; active Turns continue after the barrier. If a fixed mutable file cannot be captured consistently, fail this export and release the barrier. Do not show success until verified atomic publication. Cancellation and failure leave previous files intact; publication wins a cancellation race and returns the saved receipt.
6. Receipt: destination display name, actual bytes, creation time, package ID and included/omitted/unsupported Session status. Offer **Show file** where supported and **Done**. No background scheduler, retained catalog, automatic backup, pruning, retention or incremental chain.

## Import, validate and restore

1. **Import Profile** selects one file. Inspect in isolated staging with bounded resource use; reject archive traversal/unsafe links, malformed metadata, inconsistent hashes, database integrity failures, missing Soul/CAS closure and failed selected Session validation. Never execute package content or load package Plugins. Hashes prove internal consistency, not source authenticity: “Only import a file from a source you trust.”
2. Show file size, package creation time, format/Schema Generation, Bot count, Session facet status and privacy/deletion limitations. Separate **Data validation** from **Target readiness**. A missing target model, Plugin, credential or Workspace mapping is a readiness problem, not a corrupt package. A newer unsupported schema says **Upgrade required**; migration follows ADR-0041 in staging. Do not allow ignoring a damaged selected facet to finish a partial restore.
3. Choose **Restore as new** or **Replace existing**. Both preserve the imported identity; “as new” means a new destination Profile, not new PersonaBot IDs. The default is as new. Never merge rows with an existing Profile. Identify the destination explicitly, not by the currently selected Bot.
4. Confirmation for as new: “This preserves existing Bot identities. It does not grant permission for two copies to run.” For replacement, name the target and require an explicit **Replace [target]** confirmation: “All target Profile data will be replaced. Export it first if you need to keep it. No automatic backup or rollback file is created.” Cancel returns without target mutation.
5. Restoring must acquire the target Profile Writer Lease and run while the target Host is stopped. A running Settings page can inspect/prepare the import, but cannot replace its own live Profile. It hands off to a local portability launcher/control surface with a validated target and plan; the transport/lifecycle integration must be verified against the pinned DSH version in the first restore slice. Do not expose a generic filesystem-writing RPC from the live Client. Failure to stop or acquire the lease returns **Profile in use** with a retry after exit.
6. Progress: **Validating → Staging → Applying purge checkpoint → Committing → Restored**. Existing destination purge facts are merged monotonically before Messaging can mount; new empty targets can enforce only the package checkpoint. A selected facet failure prevents commit; original target remains intact. Atomic commit has a point of no return: cancellation is available before it, then status explains that completion is in progress. The success receipt identifies the restored destination, not a running Bot.
7. After data commit, show **Restored — setup required**. Bots remain cold. Restored or omitted historical Sessions are never automatically resumed. Selecting this file alone does not authorize activation. For an ordinary backup with no completed planned-transfer proof, use Disaster Restore safeguards before any external execution; do not label it a verified transfer merely because the user selected as new.

## Repair and explicit activation

Use one checklist grouped by capability, each row showing the desired reference, target resolution and **ready / degraded / blocked** state. These are derived Activation Readiness values, not Session activity or a second Bot lifecycle. Inspection and history stay available while execution is blocked.

| Row                               | Human action and result                                                                                                                                                                                                                                         |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Plugin capability / compatibility | Install a compatible local Plugin through the existing trusted installation path; imported manifest contains non-secret requirements, no executable installer. Recheck Host-declared critical requirements; a package cannot weaken them.                       |
| Provider identity / credential    | Reauthorize locally through the existing credential owner. Only a trusted adapter’s exact stable Provider Account Fingerprint match plus Human confirmation permits rebind. Mismatch stays blocked; matching labels or credential names do not grant access.    |
| Workspace                         | Map the saved desired reference to an existing authorized local Workspace, explicitly create/authorize a new one, or leave unavailable. Do not create a remembered path or grant filesystem access automatically; history keeps its original desired reference. |
| Model Preset / Bot Model Plan     | Preserve exact desired provider/model/effort and independent plan revisions. Resolve locally or require explicit Human remapping; no silent fallback. Remapping the target does not erase portable intent.                                                      |
| Session content                   | Show restored historical content or **Unavailable Session Reference** with its ownership and omission reason. Explicit repair/relink may reconnect later recovered content; never create empty resumable Sessions.                                              |
| External operations               | Planned transfer needs verified generation eligibility; Disaster Restore begins with Providers, bound Triggers and Service Grants suspended. Unknown in-flight external outcomes remain unknown, without replaying the old Outbox.                              |

The per-Bot action **Activate Bot** names the capabilities that will be enabled and creates a fresh Orchestrator Session only after Host revalidation and explicit Human authorization. Rebinding an external path and activating a Bot are distinct confirmations. Ready/degraded labels do not themselves run anything; a degraded Bot can activate only its ready capabilities. Dependency drift closes affected execution gates immediately, and repair never resumes work automatically.

## Planned move and disaster recovery

**Move to another device** is an option inside Export Profile, not a third unrelated catalog. Before starting: “This will stop new work here and preserve the same identities on the destination.” Source quiesces, closes ingress/external execution gates and drains or classifies in-flight work using existing lifecycle rules. Only a verified transfer file bound to a unique Transfer Generation permits the source to durably enter **Transferred out**. If preparation/export fails, no successful transfer is shown; the Host must report the actual durable source state and a safe recovery action.

The source completion page says **Transferred out — inactive on this device**, shows generation and file receipt, and offers instructions to import on the destination. Source restart, recovered credentials and archive changes never clear this gate. Destination import checks the generation and displays “Rebind local accounts and Workspaces, then activate.” It never treats package possession as current exclusive-holder proof.

The Transferred out source page offers **Cancel move**, first checking destination activation evidence. Only a verified not-yet-activated destination enables the confirmation: “Invalidate this transfer generation and restore this device’s previously authorized gates. This transfer file will no longer permit normal activation.” Action **Cancel move and restore this device**; success says **Move cancelled — this device eligible again**, with the invalidated-generation receipt and no replay of unknown in-flight outcomes. Dismissing the confirmation leaves Transferred out unchanged. If destination status cannot be verified, retain the gate and say “Cannot confirm the destination is inactive. Reconnect and retry; if it is lost, use explicit Disaster Restore.” Cancellation is refused. If activation is confirmed, say “Destination already activated; move back from that device,” with no local undo.

Transfer eligibility and cancellation are a required implementation checkpoint: bind activation evidence to the generation; cancel only after verifying target activation has not occurred and invalidating that generation. An offline file cannot prove cancellation freshness or exclusivity. If eligibility cannot be established, refuse normal activation and offer explicit Disaster Restore. Do not promise an unimplemented coordination service. Human approval of this UX does not choose a distributed protocol; the first transfer slice must document and test its concrete supported handoff before claiming planned-transfer delivery.

After confirmed target activation, the source cannot “undo” the move; move back through a reverse transfer. **Disaster Restore** says: “The original device may still be running. Activating this copy can create two holders of the same identity. Confirm that you understand this risk.” Even after acknowledgement, Providers, bound Triggers and Service Grants require separate rebind/reactivation; old Sessions and Outbox do not restart. A lost-device recovery uses this explicit path rather than silently clearing Transferred out.

## Error and confirmation matrix

Every error retains the operation summary and safe next step. Stable error codes are proposed application-defined contracts; raw paths, secrets, credentials and package content do not enter developer logs.

| Condition / phase                        | Message / next action                                                                                        | Authority outcome                                                              |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| `disk-space-insufficient` / preflight    | Not enough space; choose another authorized destination or free space, then retry.                           | No publication or target replacement.                                          |
| `destination-exists` / export            | A file already exists; choose another filename.                                                              | Existing backup stays intact.                                                  |
| `snapshot-changed` / export              | Snapshot could not be captured consistently; retry.                                                          | Barrier released; no usable partial file.                                      |
| `package-invalid` / inspect              | File is incomplete or invalid; choose a verified backup. Show bounded validation category.                   | No restore commit; never skip damaged required/selected data.                  |
| `upgrade-required` / staging             | Update to a compatible version, then inspect again.                                                          | No down-migration or partial module mount.                                     |
| `profile-in-use` / restore               | Close the target Profile and retry.                                                                          | Writer Lease refuses competing writes.                                         |
| `session-facet-unsupported` / inspect    | Selected history cannot be restored by this adapter; install a compatible adapter or choose another package. | Abort selected-facet restore; deliberate omission at export remains supported. |
| `dependency-unavailable` / readiness     | Data restored; resolve the named capability or leave it unavailable.                                         | Dependent execution blocked; history retained.                                 |
| `provider-fingerprint-mismatch` / rebind | Authorized account differs from saved identity; reconnect the matching account.                              | No external identity rebind.                                                   |
| `transfer-unverified` / activation       | Transfer eligibility cannot be verified; complete handoff or explicitly use Disaster Restore.                | No normal identity activation.                                                 |
| cancellation / before commit             | Cancelled; original data/file preserved.                                                                     | Cleanup staging only; retain durable transfer state if already changed.        |
| interruption / commit boundary           | Inspect operation/target status before retry; show committed receipt or unchanged target.                    | Host recovery, not Client optimistic success or blind replay.                  |

Host records bounded operation ID, initiator, phase, duration, result/refusal code and package/generation IDs on the existing developer diagnostics surface. Status comes from the owning module. Session flush failure, barrier timeout and publication failure are distinct diagnostic phases; private conversation content is excluded.

## Owning module and proposed Host operation requirements

The application-defined Portability deep module coordinates canonical owners: Database, Soul/Memory, CAS, Purge Ledger and the DSH Session Persistence adapter. It exposes prepared plans and operation receipts; the Client does not copy files, mutate rows or infer readiness. The trusted local launcher calls the same module for stopped-target operations. Native credential, Plugin installation, Workspace authorization and PersonaBot activation owners keep their own authority.

| Proposed operation                       | Interface requirement                                                                                                                                                                                                                                                                                                         |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Prepare export / inspect import          | Produce an opaque short-lived plan bound to source/target, package hash, selected facets and current capabilities. Return counts, size estimates, omissions and required confirmations. Recheck staleness before mutation. Human-authorized file selection resolves on the Host; no raw Client path is trusted.               |
| Execute / get status / cancel            | Human authorization plus the prepared plan; bounded operation ID and observable phase/receipt. Retrying an interrupted request first resolves that same operation’s outcome. Cancellation respects publication/commit boundary; reconnect recovers actual status. Concurrent incompatible operations refuse rather than race. |
| Get readiness / resolve target reference | Readiness is computed by canonical capability owners. Explicit local repair preserves portable desired references. No backup operation grants credentials, filesystem access or code installation.                                                                                                                            |
| Complete / cancel transfer; activate     | Require current durable Transfer Generation eligibility and owner authorization. Revalidate just before opening gates; return explicit refusal where proof is absent. Activation delegates to the PersonaBot owner and starts a fresh Session.                                                                                |

No RPC names or package layout are frozen by this proposal. Resource limits, supported Session adapters, concrete stopped-Profile handoff, migration coverage and transfer proof must be verified in their implementation slice. Sensitive operational facets remain in the complete core and are disclosed, not selectively dropped to simplify UX.

## Acceptance and subsequent vertical slices

Human acceptance checks: distinguish clone from preserved identity; understand the optional Session/privacy/size summary; choose new versus stopped-target replacement; repair a missing model/Workspace and reject an account mismatch; understand Transferred out and explicit Disaster Restore. This design PR does not supply functional E2E evidence because it changes no runtime UI. Runtime slices below each need a real DSH openable flow, focused automated failure coverage and screenshots/recording before their own Human QA and merge.

1. **Export / restore-as-new core:** audit current canonical owners first; real Settings export → one verified file → stopped-target staging restore → cold history inspection and one explicitly activated Bot’s real reply, with target-local prerequisites explicitly repaired. Include current Model Presets/independent Plans and purge checkpoint. A missing production core dependency blocks this slice; no model-only file or UI mock completion.
2. **Optional Session history and replacement:** first the real portable Session Persistence adapter include/omit/unsupported path; then staged whole stopped-target replacement, damaged-file failure preserving original target, explicit manual-backup warning and unavailable historical references. Split these into separately Human-testable tickets if needed, preserving complete-core semantics.
3. **Repair and activation coverage:** Plugin compatibility, model remap, Workspace authorization and exact provider fingerprint checks; dependency drift; explicit fresh Session activation and suspended external operations across restart. Each ticket adds one working repair path to the same restored-profile flow.
4. **Planned transfer / Disaster Restore:** source quiescence and durable gate, concrete generation handoff and activation proof, restart protection, pre-activation cancellation invalidation, post-activation reverse transfer, and acknowledged lost-device recovery without replay. No planned-transfer claim until two-real-Host evidence exists.

Publish implementation tickets only after Human accepts #76; keep it open through that ticket handoff. [#505](https://github.com/BotHarness/BotHarness/issues/505) remains blocked on production full Profile Backup/Restore and its other declared sharing contracts, not merely this design PR. This proposal does not change milestones, complete #505, or replace [#194](https://github.com/BotHarness/BotHarness/issues/194) Attention acceptance.
