---
title: Roster arrangement moves host-side (ADR-0034; spec v1.13; client-bridge v0.6)
date: 2026-09-20T10:00:00+08:00
tags: [spec, storage, client, migration]
---

- **`botharness_roster` storage domain (#66)**: the durable roster arrangement — section names, membership, order, and pins — moves from browser localStorage into the DSH storage domain `botharness_roster` on the `json` backend (`version 1`, `layout: single`): one global slot `{ pins, sectionOrder }` plus a `sections` table keyed by a host-generated uuid, `{ name, channelIds }`. The client never invents ids and never touches host files; seven fine-grained bridge methods (`rosterGet`, `sectionCreate`, `sectionRename`, `sectionRemove`, `channelAssign`, `sectionReorder`, `pinsSet`) expose the reads and writes on the `botharness` typert namespace, zod-validated, each returning after its durable write, with the client re-reading `rosterGet` after every mutation (no optimistic state).
- **Optional capability, honest degradation**: storage is an optional capability (`ctx.inject(['storageDomain'], cb)`); without it the plugin still loads and roster reads and writes both fail with `storage-unavailable` (a new `RemoteErrorDetailsMap` code) — `rosterGet` never projects a fake empty arrangement. The client renders the read-only banner on the first load and clears it when a later load succeeds.
- **One-shot migration with rollback**: when the host arrangement is empty and a legacy browser `roster.json` exists, the client creates each section in legacy order, assigns its channels in order, applies the section order and pins, and re-keys the `ui-bot-mode` `sortModes` from legacy ids to the host-generated ids. Any failure rolls back the sections and pins this run wrote so the host stays empty and the next load retries cleanly; only full success backs the legacy record up (`botharness/roster.json.backup`), clears the live key to `{ collapsed }`, and writes `botharness/roster.migrated`. Only `collapsed` stays browser-local; the #55 manual-order seam now freezes order through positioned `channelAssign` calls instead of the local `channels` array.
- Spec v1.13 (§2.1/§5) and client-bridge v0.6 (nineteen methods, the new error code) carry the change; ADR-0034's consequence list and temporary-seam update are corrected.
