## 1. 结论摘要

- **主体合规**：M2 的工具（`defineTool`/`output.render`/`execute` 抛错语义）、系统提示词 section（命名、动态 provider、排序）、生命周期（自动 dispose、无需 `ctx.effect`）、bundle manifest（`dsh.bundle.patch` + 按包名引用的 `cordis.patch.yml`）均符合上游文档的一手规定。
- **必须调整 3 类**：
  1. **插件配置通道错了**：上游 `/develop/basic/config` 规定「导出 `Config` schema + `apply(ctx, config)`」（`config` 由 `cordis.yml` 的 `config:` 块提供）；我们用 `ctx.settings.register('botharness', Config, { base })`（`packages/core/src/plugin.ts:57`），而 `apply` 不接收也不消费 `config`——`enabled` 是**死配置**。`ctx.settings` 是「用户设置 seam」，不是插件 composition 配置的入口。
  2. **settings 消费方应注册 `installSection`，且应软注入**：官方 cookbook 明确「已经有 cordis.yml entry 的消费方应通过 `ctx.settings.installSection()` 注册」；我们反而把它写进静态 `inject = ['settings', …]`（`plugin.ts:19`），在没有 settings provider 的组合（如 `sdk-minimal` profile）里插件会永久 PENDING，连工具和提示词都不加载（上游 CLI 参考确认 base 系 profile 才挂 settings provider）。
  3. **兼容声明字段非官方**：`package.json` 的 `dsh.compatibility.dsh`（`packages/core/package.json:35-37`）不是 `DshManifest` 的字段；官方字段是 `engines.dsh`（SemVer，可写精确预发布版本）与 `dsh.manifestVersion`（`@deepseek-ai/dsh-package-manifest` README）。两者都不被当前安装器强制，但声明应写对字段。
- **Service/`ctx.provide` 合规**：`ctx.provide('botharness', core)` 是 Cordis 一等 API（注册随 fiber 自动撤销），函数形态无需改成 `Service` 子类；缺 `declare module '@deepseek-ai/cordis'` 类型合并只影响消费方类型安全（建议补）。
- **M3 约束**：client 半必须声明 `dsh.client` 并导出构建产物 `./client`、第三方依赖自包含、slot 用 `ctx.slots.inject`/`register`、不能跨插件 import 运行时值；命令用 `ctx.commands.register`（小写、无斜杠、handler 收到精确 agent）；composer `@` 上游**没有**一等 mention API，需用 composer 系 slot（`conversation.input.*`）自行实现。

## 3. 必须调整项

### 3.1 用官方通道消费插件配置（`packages/core/src/plugin.ts`、`packages/core/cordis.patch.yml`）

- **现状**：`apply(ctx)` 单参（`plugin.ts:56`），`Config` 只在 `settings.register` 里当 schema 用（`:57`），`enabled` 永不生效；用户在 bundle patch 里写 `config:` 会通过 schema 校验但被忽略。
- **改法**（与官方 `/develop/basic/config` 示例同形）：

  ```ts
  export function apply(ctx: Context, config: BotHarnessConfig): void {
    if (!config.enabled) return;
    // …注册工具与提示词段…
  }
  ```

  同时把 `cordis.patch.yml` 的行保持无 `config`（用户/上层 bundle 可覆盖），并删除 `DEFAULT_CONFIG` 的「第二事实源」角色或仅作为 `Config` 默认值来源（schema 默认值已足够）。

- **注意**：patch 的层叠会**整段替换** `config` 而非深合并（`/develop/basic/publish.md` 加载顺序节），所以 schema 默认值必须能补齐用户省略的字段（现状满足）。

### 3.2 settings namespace 改用 `installSection` + 动态注入（`packages/core/src/plugin.ts`、`packages/core/package.json`)

- **现状**：静态 `inject` 含 `'settings'`（`plugin.ts:19`）→ 没有 settings provider 的组合里插件 PENDING；`ctx.settings.register`（`:57`）是 owner 路径且返回值（`SettingsScope`）被丢弃，`enabled` 无法热更新。
- **改法**（官方 cookbook §1 的消费方形态）：
  1. 从 `inject` 移除 `'settings'`（`inject = ['tools','systemPrompt']`），或若必须保留 settings 依赖，则在文档与 M3.5 里明确该插件只在 base 系 profile 可用。
  2. 若要把配置暴露到 Settings → Plugins 页（M3+ 的 settings card），用：

     ```ts
     ctx.inject(['settings'], (settingsCtx) => {
       settingsCtx.settings.installSection(ctx, SETTINGS_NAMESPACE, Config, config, {
         setSource: (current) => {
           source = current;
         },
         onChange: () => {
           /* 重新判断 enabled / 重建派生状态 */
         },
       });
     });
     ```

     这样 provider 缺席时回退到 `config`（composition entry），provider 在场时用户分区叠加在 entry 之上。

  3. 若暂时不需要 UI 设置，最简做法是**完全不注册 namespace**，只保留 `apply(ctx, config)`；等 M3 真做设置卡片时再按 cookbook 补 Host 半 + client 半（两半用同一 namespace 键自动配对）。
- **连带**：`SETTINGS_NAMESPACE = 'botharness'` 合法（小写 kebab-case 校验，单段合法；`dsh-settings/types/index.d.ts:15-19`），可保留。

### 3.3 兼容声明改为官方字段（`packages/core/package.json:35-37`）

- 删除 `"dsh": { "compatibility": { "dsh": "0.1.5-alpha.1" } }`（无任何官方 reader 读取）。
- 在 `package.json` 顶层加 `"engines": { "node": ">=22", "dsh": "0.1.5-rc.2" }`（`engines.dsh` 与 `engines.node` 并列；可写精确预发布版本），并在 `dsh` 下加 `"manifestVersion": 1` 与既有 `bundle` 并列。
- **值的选择**：应与 M3.5 验证门实际钉住的宿主一致（并行文档建议 `@deepseek-ai/dsh@0.1.5-rc.2`）；当前写 `0.1.5-alpha.1` 既非官方字段，也和全部 `0.1.5-rc.2` 的 devDeps 不一致。注意该声明当前**不被强制**，只是作者意图（`@deepseek-ai/dsh-package-manifest` README「兼容性仅作声明」）。

### 3.4 M3 开工前必须落实的规范约束（M3 代码尚未存在）

1. **客户端包**：`dsh.client`（`platform: 'web'`）+ `exports['./client']` 指向构建产物；`@botharness/client` 的第三方依赖（如 avatar 库）必须打进 bundle，不能假设宿主提供；bundle 采用 lazy-CJS factory 契约（官方 preset `packages/client/tsdown.client.ts` 是仓库内部文件，外部包需复刻；未验证是否存在已发布的第三方 preset）。
2. **slots**：roster 面板注册 `sidebar.panellist`（list + `id`）并用同一 `id` 提供 layout root `main` 的 keyed 组件；`ctx.slots.inject(key, () => ctx.slots.register(...))`，禁止模块级副作用；跨包只允许 `import type`，禁止值导入（bundle purity gate）。
3. **commands**：`/bot` 用 `ctx.commands.register`，`name` 小写、不带 `/`，`handler` 收到精确 `agent`；命令不产生模型消息，结果直接给 UI；生命周期随 fiber。
4. **composer @**：上游无 mention API，需基于 `conversation.input.*`/`conversation.composer.*` slot 自建选择器，并把「选中 PersonaBot」编码为插件自有事件或命令参数；PRD 已知「@ 源全局跨会话」为 PoC 限制，M3 可维持。
5. **状态事件**：M3 接 `ctx.on('agent/*')`（`agent/status`、`agent/created`、`agent/disposed`、`session/event` 等）驱动 roster，注册必须在插件 fiber 上（自动清理）。
6. **bundle 打包**：M3.5 安装对象建议合并为单一 `deepseekbot` bundle（内部依赖 core/client），避免逐包安装的层叠顺序问题（并行文档 §6.4.2）。

## 4. 建议但可选

1. **服务类型面**：在 `plugin.ts` 增加 `declare module '@deepseek-ai/cordis' { interface Context { botharness: BotHarnessCore } }`，或当 M3 需要从 client 侧经 Remote 读取时，把核心对象升级为 `Service` 子类（教程 03 的类形态）。运行时行为不变。
2. **工具卡片**：`memory_read`/`memory_search` 可加 `presentCall`/`presentResult`（`read`/`search` 卡片）与 `output.presentationMeta`，让 Web Client 有结构化展示；只定义 Host 展示方法不会自动产生专用 Web 卡片（`/reference/cookbook/adding-a-tool.md`「Web Client 展示」节）。
3. **并发与超时**：`memory_read/search/list` 只读、可标记 `isConcurrencySafe: () => true`；若声明 `timeoutMs`，必须同时把 `exec.signal` 接入 I/O（当前同步路径做不到，需先异步化）；不声明则维持现状（独占、无截止时间），语义安全。
4. **依赖归属**：`@deepseek-ai/schemastery`、`yaml` 目前被打进 dist（302KB，含 cosmokit）。仓库内约定 `schemastery` 应作 `dependencies`；对外部包可权衡：上移为 `dependencies` + `external` 可减小产物，但 profile `autoInstallPeers: false` 下普通依赖会被 pnpm 正常安装；已确认 `dsh-settings` 运行时不使用 `instanceof`（计数 0），打包副本无已知功能风险（未做运行时验证）。
5. **`exports` 增加 types**：`"exports": { ".": { "types": "./dist/index.d.mts", "default": "./dist/index.mjs" } }`，确保消费方（M3 的 app 包）拿到类型。
6. **`engines.node`**：DSH 本体要求 `^22.19.0 || >=24`（并行文档 §5.2）；我们的 `>=22` 偏松，建议对齐。
7. **工具领域语义**：`memory_read` 对不存在的文件可考虑返回规范值（如 `{ found: false }`）而非抛错，以贴合「成功领域结果写规范值」的原则；当前抛错也被注册表正常转为 `isError`，非违规。
8. **`external` 列表清理**：`dsh-system-prompt`/`dsh-agent` 是纯 type import，被 tsdown 自动擦除；列入 external 无害但会误导读者，可在 M3 重构时清理或注释原因。
9. **发布形态**：`private: true` 对本地 `link:`/tarball 无影响；若 M3.5 后走 npm，需要去掉 `private` 并补 `publishConfig`（并行文档 §6.4）。

## 5. 未验证/待确认

1. **未运行 DSH**：所有运行时行为（HMR 替换、`installSection` 在 provider 缺席时的回退、slot 渲染）均由文档与类型声明推导；M3.5 安装门应实测。
2. **`ctx.inject` 动态注入的确切语义**：官方 cookbook 使用 `ctx.inject(['settings'], cb)`，Cordis 源码中存在该 API（`cordis/src/registry.ts:51`），但「回调用父 ctx 还是子 ctx 做 owner」在不同版本间是否有差异未逐一验证（cookbook 示例传父 `ctx` 作 owner）。
3. **`base` profile 是否必然挂 settings provider**：CLI 参考说 base 系「挂载 settings 与凭据提供方」，`sdk-minimal` 明确没有；`headless`/`acp` 是否同 base 未逐 profile 验证（并行文档 §1.3/§6.1 同结论）。
4. **版本号可得性**：`npm registry` 的 `@deepseek-ai/dsh-settings/latest` 当前指向 `0.0.1-rc.1`，而本仓库锁定 `0.1.5-alpha.1`；tag/镜像差异原因未查清。这会影响 3.2 里 cookbook 所示 API 与宿主实际版本是否一致。
5. **工具命名是否被硬性校验**：文档只说唯一与保留 `run_code`，未给出 snake_case 正则；「snake_case 是惯例」为一手示例归纳，非规范条文。
6. **composer @ 的推荐落点**：上游没有 mention 文档；`conversation.input.overlay` vs `conversation.input.left/right` 哪个更适合 @ 选择器未验证，属 M3 设计问题。
7. **客户端第三方构建 preset**：官方共享 preset 为仓库内部文件，外部包「复刻同样输出格式」的可行性只有并行文档的文档级推导（并行文档 §4.1/§7.4）。
8. **第 3.3 条 `engines.dsh` 范围写法**：精确预发布版本在 pnpm/安装器下的比较行为不被强制，未实测。
