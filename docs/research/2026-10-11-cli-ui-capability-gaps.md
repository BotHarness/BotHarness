# CLI as a non-UI debug and test Consumer: current capability gaps

## Scope and evidence

Date: 2026-10-11. Source baseline: `51058d540f52de45e687f4274f3d16dd701dd0d5` (main). This is a source investigation for the Human's CLI parity discussion, not an accepted architecture decision or implementation plan. No Host was started, no credentials were read, and no live provider behavior was verified in this investigation.

The source links below are pinned to that baseline. “Exists” means the production owner/adapter is in source; it does not mean this investigation has qualified the behavior on a running Host. Proposed command spellings and sequencing are recommendations requiring Human decisions.

The CLI should be another **Consumer** of an existing application-defined Service Definition/Provider, not a second owner or direct live-database writer. DSH SessionEvent/Session Persistence owns Agent execution history; application-defined Source Events, Inbox Admissions and Channel placements own Messaging facts. These are different authorities. See [DSH Context](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/.agents/skills/dsh-plugin-dev/references/context.md#capability-seam), [Decision Tree](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/.agents/skills/dsh-plugin-dev/references/decision-tree.md#6-choose-the-persistence-authority), and [product Source Event terminology](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/CONTEXT.md#L405).

## Action gaps grouped by existing owner and seam

### PersonaBot Deletion: scope preview, confirmation, outcome

The production owner is `createPersonaBotDeletions`; Bridge remote methods already expose `deletionPreview`, `deletionConfirm`, `deletionRetry`, and `deletionMemoryFolder`. There is no direct Registry removal path: it throws and requires confirmed PersonaBot Deletion. [Definition](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/packages/core/src/bots/deletion.ts#L19), [Bridge](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/packages/core/src/bridge/methods.ts#L1760), [Registry](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/packages/core/src/bots/registry.ts#L526).

Important distinctions for a CLI Consumer:

- Opening the UI's deletion dialog only requests a preview; it does not accept deletion. Confirmation passes the reviewed token and explicit `eraseMemory` boolean. [UI](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/packages/client/src/client/personabot-deletion.tsx#L32), [confirmation](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/packages/client/src/client/personabot-deletion.tsx#L200).
- Preview includes dependencies (Sessions, Workspaces, Grants, identities, Channels), Memory path, erasure refusal and a hash of the current scope. A changed scope invalidates confirmation. Accepted deletion immediately removes the identity from active Registry lookups while historical identity remains. [preview/confirm](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/packages/core/src/bots/deletion.ts#L226), [active lookup gate](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/packages/core/src/bots/registry.ts#L255).
- Stopping cancels Group invitations, revokes Workspace Grants and Tool rules, stops the Bot runtime, and disables external Messaging. It is not a list-row removal. The owner records `stopping → cleanup → complete`, or `incomplete` with retry; optional Memory erasure validates canonical ownership and overlap protections. [composition effects](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/packages/core/src/plugin.ts#L690), [owner outcome](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/packages/core/src/bots/deletion.ts#L251).
- Deletion retains attribution and defaults to retaining Memory. It is distinct from reversible archiving and from Content Purge. A CLI must not claim “all private data erased” from a successful deletion receipt. [product definitions](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/CONTEXT.md#L12).

Recommendation: expose preview, explicit token confirmation, inspectable phases and retry as one lifecycle slice. Keep Memory erasure opt-in. Whether CLI confirmation should require a separate command or an explicit reviewed token is a Human-facing contract decision, not an implementation fact settled here.

### Messaging Content Purge: a separate destructive capability

Existing methods are `channelHistory`, `channelHistorySources`, `channelPurgePreview`, `channelPurgeConfirm`. Preview identifies placements, Admissions, files, Outbox/Assignment/causal effects and Memory/Workspace derivatives. Confirmation requires a signed five-minute scope token; it records a monotonic Purge Ledger and applies cleanup, potentially returning `cleanupPending`. [remote methods](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/packages/core/src/bridge/methods.ts#L2803), [contracts](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/packages/core/src/purge/contracts.ts#L81), [owner confirmation](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/packages/core/src/purge/owner.ts#L464).

This confirm contract is Content Purge, not a general “Purge Everywhere” operation: it takes no option to delete disclosed Memory/Workspace derivatives. The Context also explicitly distinguishes the latter and says unmanaged copies remain the Human's responsibility. [Context](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/CONTEXT.md#L537).

Recommendation: treat privacy purge as its own reviewed slice, not a `delete --all` convenience flag. Whether it belongs in the first parity tranche is an unresolved priority decision.

### Bot sharing/export and import

Bot Zip already has a production exact authenticated Fetch Registration: `/api/botharness/bot-zip`, `/files`, and `/import`. Export accepts all files with optional Git history, or a selected file set without history. The descriptor plus its referenced Avatar and banner are always included when present. Bounds are 100 MiB and 20,000 entries; `.git` itself is excluded, with optional history represented by a Git bundle. [HTTP implementation](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/packages/core/src/bots/bot-zip-http.ts#L100), [bundle implementation](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/packages/core/src/bots/bot-zip.ts#L20), [Registration](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/packages/core/src/plugin.ts#L1614).

Import validates the archive and creates a fresh Host-generated PersonaBot identity using `registry.createFromFiles`; current CLI `create --from-zip/--from-dir` already consumes the bundle shape offline. [HTTP import](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/packages/core/src/bots/bot-zip-http.ts#L168), [CLI help](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/packages/core/src/bots/bot-create-cli.ts#L174).

Do not revive the retired “PersonaBot Export” operational-facet package under this feature name: current product sharing is Memory Git/Bot Zip, while whole Profile transfer has Profile Backup. Bot Zip is not a live clone of Sessions, credentials, IM grants or operational history. [Context sharing definitions](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/CONTEXT.md#L318), [Profile Backup owner](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/packages/core/src/portability/package.ts#L298).

Recommendation: wrap existing binary export/import endpoints with file output/input plus bounded JSON receipts. Human must decide whether “export” means shareable Memory only or a broader archive; these have different owners and privacy scope.

### Avatar, Profile Banner and presentation

`botAvatarSet`, `botBannerSet` and `botAppearanceSet` already delegate to Registry/presentation owners through the Bot's DM context. Avatar input is a bounded PNG/JPEG/WebP data URL or null reset; banner is a valid recipe/image or null reseed; appearance is validated structured data. Group Avatar has its own `channelGroupAvatarSet`. Part Library list/add/export/import/image-import is also a distinct capability family. [DM scope](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/packages/core/src/bridge/methods.ts#L1005), [appearance/parts](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/packages/core/src/bridge/methods.ts#L2249), [banner/avatar](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/packages/core/src/bridge/methods.ts#L2423), [Client consumers](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/packages/client/src/client/bridge.ts#L1968).

Recommendation: CLI sets/resets a file or validated appearance/banner recipe and reports persisted metadata/hash, avoiding huge base64 output. Crop/resize previews, appearance editor layout and animation correctness remain visual UI acceptance. Roster pin/hide/order and Window Companion are presentation preferences, so whether to expose them is an explicit parity-scope choice rather than a prerequisite for headless runtime testing. Existing roster methods are listed in the [Service Definition](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/packages/core/src/bridge/methods.ts#L529).

## Acceptance branches requiring a Human decision

1. **Meaning of headless parity.** Recommended: non-UI product commands and owner-based reads share the same production Host capabilities as the browser. Do not make “every preference can be changed” the gate for the first runtime/debug slice.
2. **Meaning of success.** Recommended: every test states its required boundary: persisted configuration, accepted Admission, handled Admission, durable correlated reply, Provider acceptance, or externally visible delivery. They are not interchangeable. A generic zero exit code or `accepted: true` is insufficient for all of them.
3. **Live first versus offline maintenance.** Recommended: debug/test scenarios use one isolated running Host; retain offline operations as explicitly documented maintenance paths. Online discovery is needed even before broad command migration.
4. **Export scope.** Recommended: first wrap current shareable Memory/Bot Zip semantics. Messaging Archive or whole Profile Backup is a separately scoped need; do not silently import active permissions or credentials with a Bot.
5. **Destructive parity scope.** Recommended: Bot deletion with retained Memory first; Memory erasure and Content Purge remain distinct explicit reviewed operations. Do not use deletion as test cleanup until the fixture ownership is established.
6. **External test evidence.** Recommended: CLI replaces internal message composition, owner introspection and polling; real external inbound tests still enter through the qualified Provider's trusted route. Human QR/login/platform permission steps and required visible delivery proof remain real. A synthetic local Source Event can test an internal owner boundary but must never be reported as a successful real-provider chain.
7. **Presentation priority.** Recommended: Avatar/banner/appearance file/recipe parity after the first lifecycle + Group/IM chain. Browser checks remain for crop, editor, animation, layout, usability and actual platform rendering. The first parity tranche does not need roster/companion UI preferences unless the Human wants full interaction parity.

No decision in this section is approved by this investigation. The next step is to settle the scope and required evidence with the Human, then choose one production-shaped tracer bullet. The [repo delivery workflow](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/AGENTS.md#delivery-workflow--tracer-bullets) requires validating that vertical slice and seeking Human feedback before expanding siblings.
