## Image fixed points, size and updates

The real QA uses the previously cached image by immutable digest:

- Digest: `lscr.io/linuxserver/webtop@sha256:c4ceafc1c48ed9a61771345c74568d3bff6438802f0d89e9ebd9846e8404f696`.
- Local image ID: `sha256:896878e282e35a09d87e28c114fc13a9f73edc1dd13f863d57c537dc29df86a1`; source `9fb3ff5479a0afcd840711c3a8de4d05f3170bf5`, version `621de5cf-ls1`, built 2026-09-15. Local image size: **3,293,386,912 bytes**. This is image size, not measured network download.
- Current registry `ubuntu-xfce` index observed separately: `sha256:e839dc471a0e54b32066d84b4f081a212e50c43d0644351a0ae4c58eacaa37eb`, source `9212cb58831a8e1d2b0174ed815c0ef270a95d35`, version `b0345a66-ls4`. Compressed layer descriptors sum to **1,247,510,139 bytes arm64** and **1,279,669,879 bytes amd64**, excluding metadata/transport overhead and cache effects. This newer image was researched, **not pulled or run**. [Sanitized registry descriptors](../assets/pr/205-computer-image/registry-proof.json).

[Docker SIZE documentation](https://docs.docker.com/reference/cli/docker/image/ls/#description) and [layer reuse/digest semantics](https://docs.docker.com/reference/cli/docker/image/pull/) distinguish these measurements. The previous approximate 1.5 GB pull estimate is not a hard ceiling or an invariant of a mutable tag.

Current BotHarness defaults use a mutable tag, inspect the local image before pulling, and compare the configured image string when deciding to recreate. They do not track remote digest changes for an unchanged tag. For a reproducible deployment, explicitly configure a validated digest, then deliberately update/recreate and verify the narrow desktop/profile path. An architecture-neutral deployment should qualify the multi-platform index and its relevant platform manifests. Do not set a newly researched digest as the global default without runtime verification; pinning also delays security fixes until the pin is advanced. This is deployment guidance, not a new automatic-update implementation. [LinuxServer update procedure](https://docs.linuxserver.io/general/updating-our-containers/), [official webtop](https://docs.linuxserver.io/images/docker-webtop/).

## Seeds and upstream compatibility boundaries

The existing Provider reapplies executable shortcut, session-restore policy, launcher shims and workspace after start. Real QA confirmed `/config/workspace`, executable `/config/Desktop/chromium.desktop` and `RestoreOnStartup: 1` after import/restart. After the existing-volume restart, panel values were icon-size 32 / size 52; that does **not** prove a fresh volume receives the same sizing on its first start.

The operations remain best effort; successful startup alone is not proof that every seed succeeded. `ensureDesktopDefaults` edits an already present XFCE XML before start, always through the configured named volume, whereas the Provider can separately choose a Linux bind store. This macOS/named-volume qualification does not validate that bind-store path. [Pinned Provider source](https://github.com/BotHarness/BotHarness/blob/d993f57448a48738cc365b9d601f459f67be35af/packages/computer/src/providers/docker.ts).

Current upstream [XFCE startup](https://github.com/linuxserver/docker-webtop/blob/9212cb58831a8e1d2b0174ed815c0ef270a95d35/root/defaults/startwm.sh) copies defaults only when the complete per-channel directory is absent; a thin layer does not repair missing files or migrate old preferences by itself. Official [custom init scripts](https://docs.linuxserver.io/general/container-customization/#custom-scripts) can run before services, but customization remains downstream-owned and still needs migration/idempotence validation.

The newer upstream [desktop launcher](https://github.com/linuxserver/docker-webtop/blob/9212cb58831a8e1d2b0174ed815c0ef270a95d35/Dockerfile.aarch64) uses [wrapped-chromium](https://github.com/linuxserver/docker-webtop/blob/9212cb58831a8e1d2b0174ed815c0ef270a95d35/root/usr/local/bin/wrapped-chromium) and absolute `/usr/bin/chromium`, so BotHarness `/usr/local/bin/chromium` shims alone do not prove those flags apply to desktop-launcher starts. The QA deliberately launched that local shim; it does not qualify the newer launcher. These are explicit verification gaps for a future image update or initialization slice, not evidence that a derived image is necessary.

Keep the current upstream XFCE/Chromium/Selkies stack. Resource defaults in the current source are 2 CPUs / 4 GiB memory / 512 MiB shared memory / 4096 PIDs / 1280×800 / 30-minute idle policy. Earlier ADR measurements are historical, not refreshed cross-platform memory or startup claims. Upstream webtop defaults to no authentication and exposes a desktop terminal with passwordless sudo; BotHarness's loopback endpoint and authenticated Host proxy remain essential. Custom desktop hardening is not an authentication substitute. [Upstream authentication](https://docs.linuxserver.io/selkies/user-guide/security/#authentication-layers).

## Real functional E2E

This was **Host/API + real Docker + actual Human Viewer E2E**, not a PersonaBot model trial. No product code changed; there is no model-completion or screenshot-semantic accuracy claim. Browser Access stayed disabled on the synthetic `Computer Image QA` Bot.

1. Boot an isolated Profile through the pinned AX launcher, explicitly select Container, and assign unique QA container/volume, loopback port and private export directory. Verify the active container's `/config` mount matches that exact disposable volume.
2. Start through authenticated `/api/computer/start` with explicit authorization, wait for actual running status, and prepare two synthetic files under `~/workspace/205-qa`. Launch real Chromium against the file fixture; view it in the existing authenticated, watch-only fullscreen Computer Viewer.
3. Export through authenticated `/api/computer/export`. Ten Chromium processes were present before export. The archive contains the two exact original files; independently read them from the tar and compute SHA-256. The Host restarts the desktop after export.
4. Overwrite both disposable fixture files with `changed-after-export`; independently read back the marker. Import the known archive through `/api/computer/import`; confirm running and exact restored hashes. The archive, original and restored hashes agree for both files.
5. Verify unauthorized export/import and a `../bad.tar` request are refused. Explicitly relaunch Chromium against the **restored file**, reconnect the actual Viewer, and capture the restored state. Do not interpret this as automatic browser-window restoration.

[Runtime proof](../assets/pr/205-computer-image/runtime-proof.json) records the image, archived Chromium state, hashes and refusals. Existing-container authorized start took 2689 ms; export 4326 ms; import 4076 ms; archive 134,062,080 bytes. One warm trial is descriptive, not a cold-pull benchmark or a seconds-start guarantee.

[Before export](../assets/pr/205-computer-image/before-export.png) and [after restore](../assets/pr/205-computer-image/after-restore.png) are real 1280×720 English/light fullscreen Viewer screenshots from the same Bot/Profile/fixture. They show runtime phases of unchanged UI, not a redesign. The independent hashes establish persistence; the static fixture caption alone does not.

### Failures and limitations

- The first QA helper incorrectly treated accepted start as synchronously running; waiting for the existing asynchronous status fixed the probe. Its first `rpcId` was numeric, refused by the native Gateway; a string made the synthetic Bot setup succeed. No production workaround or new API was added.
- Initial QA idle time 0 is clamped to one minute by existing code, rather than disabling idle stop. That stopped the owned container before the first round-trip attempt. The attempted verification failed and is disclosed; the corrected QA Profile used 60 minutes and the reported full round trip passed. Only the exact task-owned Host was restarted.
- Archived Chromium `exit_type` stayed `Crashed`, and the real restored Viewer shows “Chromium didn’t shut down correctly”; do not assert clean browser flush, universal SQLite consistency, session restoration or crash/power-loss protection. Workspace files did round-trip. The accepted fallback contract remains explicit.
- Named-volume/macOS arm64 only; no Linux bind, Windows Host, headless VPS, current upstream image execution, automatic update, fresh-volume panel guarantee, model perception, cost comparison or clipboard claim.

The existing Docker-provider/export regression passed **59 tests**. Research/verification documentation adds no runtime behavior or new tests. Full published-head CI is reported in the PR separately.
