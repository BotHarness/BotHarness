# CLI five-platform IM chain: facts and design frontier

Date: 2026-10-11. BotHarness baseline: `51058d54` on main. Qualified Provider: `@xmanrui/dsh-im` 4.32.0, source `bddd7d93e1c1b969ce137721c2494f6d72bfa8bc`, DSH `0.2.0-rc.1`. This is a source investigation and a proposal for discussion, not an implementation contract or a new live qualification. No Provider authorization, credential access, external message, or Host launch was performed for this investigation. The existing P3 evidence is identified separately below. The composition pin comes from [dev-im-provider.mjs](../../scripts/dev-im-provider.mjs).

## Finding

The five platforms already have BotHarness Provider adapters and native account capabilities. The CLI currently exposes only the Feishu/WeChat application-authorization adapter, and its `im-apps` command returns compatible setup Providers rather than authenticated Apps. Adding the complete chain should expose existing Host owners and native Provider owners; it does not require a second IM account store, fake inbound RPC, or a new message receiver in the CLI. Source: [Plugin Provider registration](../../packages/core/src/plugin.ts), [current CLI projection](../../packages/core/src/bots/cli-im-authorization.ts), [Messaging Provider adapter](../../packages/core/src/messaging/dsh-im.ts).

An internal `send` to a PersonaBot DM can exercise a real Host, Bot Inbox, Orchestrator, and committed Channel reply without using the browser. It cannot prove that a third-party platform delivered an inbound event, that a native permission permits ordinary group traffic, or that a platform rendered a sent message. Those require the actual external boundary. See [CLI guide](../bot-cli.md), [AGENTS.md IM browser QA](../../AGENTS.md), and [checked inbound event contract](../../packages/core/src/messaging/provider.ts).

## Authorities and terms

The DSH/Cordis seam is **CLI Consumer → authenticated Connection/API Gateway → application-defined Service Definition → owning Host Provider**. Provider setup separately calls the Provider-owned `dsh-im/app-setup` exact authenticated Fetch Registration. Cordis Plugin/Fiber ownership controls the live registrations and receiver cleanup. Durable product records remain in the existing operational database; native secrets and account configuration remain Provider-owned. Source: [DSH Context](../../.agents/skills/dsh-plugin-dev/references/context.md), [Decision Tree](../../.agents/skills/dsh-plugin-dev/references/decision-tree.md), [ADR-0161](../adr/0161-cli-im-authorization-keeps-provider-attempt-authority.md), [Client Provider setup consumer](../../packages/client/src/client/provider-app-setup.ts).

The following operations are distinct:

| Operation                                      | Authority and effect                                                                                                                                                                   |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| IM 应用授权                                    | Authenticates a native Provider account/App. A ready account does not choose a PersonaBot. Credentials stay in the native owner.                                                       |
| PersonaBot external identity Binding           | Persists `providerId`, `accountRef`, verified account fingerprint, owning PersonaBot and enabled/revision facts in `messaging_bindings`; one App can belong to at most one PersonaBot. |
| Workspace Grant                                | Grants PersonaBot access to a resolved local Workspace. It neither grants IM account ownership nor conversation messaging.                                                             |
| Messaging Grant / Conversation entry           | Records one Binding's conversation, explicit send target or implicit admitted default traffic, reception policies and optional Channel route.                                          |
| Conversation ingest                            | Channel-owned inbound-only connection, with context-only admission by default. It gives a PersonaBot no reply authority.                                                               |
| Source Event / Inbox Admission / Outbox Intent | Canonical received content, admission into PersonaBot attention, and tracked outbound operation, respectively. Execution history remains DSH Session history.                          |

These definitions follow [root CONTEXT](../../CONTEXT.md), [Messaging identity contract](../../packages/core/src/messaging/identity.ts), [Messaging service/Grant contract](../../packages/core/src/messaging/outbound.ts), and [Provider events/reply routes](../../packages/core/src/messaging/provider.ts). Product Binding must not be called IM application authorization. Native dsh-im APIs sometimes use `bindCredentials` for credential import; that native name is not the product Binding.

## Account handoff is a lifecycle, not just a stored Binding

Binding commits the durable product record and invokes `reconcileBinding`. The live receiver verifies the account fingerprint and connectivity, then acquires Provider `consumeInbound`. Each of Slack, Discord's shared token controller, and QQ persists `consumerMode: external-consumer` and restarts its native runtime after obtaining the exclusive consumer Registration. The receiver Registration is process-local; consumer mode is durable. On Provider replacement, Binding disable/unbind, Bot disable or Host shutdown, the BotHarness lease aborts/disposes. Source: [Binding implementation](../../packages/core/src/messaging/outbound.ts), [reconcile/startControl](../../packages/core/src/messaging/inbound.ts), [Slack controller](https://github.com/DoodleBears/dsh-im/blob/bddd7d93e1c1b969ce137721c2494f6d72bfa8bc/src/channels/slack/slack-controller.mjs), [Discord shared controller](https://github.com/DoodleBears/dsh-im/blob/bddd7d93e1c1b969ce137721c2494f6d72bfa8bc/src/channels/shared/token-bot-controller.mjs), [QQ controller](https://github.com/DoodleBears/dsh-im/blob/bddd7d93e1c1b969ce137721c2494f6d72bfa8bc/src/channels/qq/qq-controller.mjs).

Consequences for a future chain (inferences from these owners):

- Application authorized, Binding committed, and receiver ready are separately observable states. A successful bind response alone is not enough for a receive/reply acceptance test; require snapshot `reception: receiving`, then a correlated Source Event and reply.
- Importing a new Slack/Discord/QQ account through its ordinary native management RPC can initially start standalone native consumption. The existing two-platform AppSetup explicitly starts external-consumer mode before product Binding. A unified five-platform flow must either extend that Provider-owned contract or explicitly account for the interval before product receiver handoff. Do not let the CLI write native config files to bypass it.
- Dispose/unbind does not automatically set native consumer mode back to standalone-session. A cleanup workflow must not promise automatic native reply restoration; verify the intended post-cleanup account mode and actual replies.
- Binding conflicts and stale revisions/fingerprints are useful safety contracts, not errors to bypass by selecting the most recently discovered account. Existing production accounts and exclusive receiver changes need their own authorized window and restoration plan, as required by AGENTS.md.

The existing CLI application-authorization attempt is Provider-owned and process-local: bounded TTL, opaque attempt ID, independent polling, expiry on Host restart. Cancelling a ready attempt retains the authenticated account; it does not revoke credentials or delete the native App. That same status must not be reused as “full-chain complete.” Source: [AppSetup](https://github.com/DoodleBears/dsh-im/blob/bddd7d93e1c1b969ce137721c2494f6d72bfa8bc/plugin-src/host/app-setup.mjs), [CLI guide](../bot-cli.md), [P3 recorded evidence](../evidence/issue-1318/im-authorization-cli.md).

## Testing boundary

The baseline repository instruction is explicit: [AGENTS.md IM browser QA, lines 49–55](https://github.com/BotHarness/DeepSeekBot/blob/51058d540f52de45e687f4274f3d16dd701dd0d5/AGENTS.md#L49-L55) requires correlating visible replies/reactions with canonical Source Event, Admission and Outbox facts, and states that API success alone does not verify rendering. The same section specifically requires authorization for app permission changes and exclusive production-receiver windows, cutoff/restore guards, and normal-reply verification after restoration. These are repository requirements; the implementation sequencing and cleanup choices below are proposals. Current session tool instructions govern which collaborative browser is used and take precedence over the section's older browser preference.

The desired trace should correlate concrete authorities:

```text
native account verified → product Binding → receiver Registration ready
external Human-origin message → canonical Source Event → Inbox Admission
→ Orchestrator execution → authorized Reply Route → Outbox Intent
→ Provider receipt → external observation when needed
```

This chain can be driven and inspected largely through a CLI. However, a CLI-created internal Channel message is not a real external Human-origin event. No current production `messagingSource`/send API permits callers to invent trusted native inbound context. For deterministic tests, use a qualified test Provider/fixture through the same production Service seam, with distinct evidence classification. For real third-party E2E, obtain an actual source message via an authorized Human client, external test sender or designated browser conversation. A Provider reply acknowledgement is not necessarily recipient visibility/read success. Sources: [trusted inbound contract](../../packages/core/src/messaging/provider.ts), [inbound identity validation](../../packages/core/src/messaging/inbound.ts), [AGENTS.md](../../AGENTS.md).

Channel history alone is insufficient for an external Inbox-only route. An external Binding may admit a Source Event into the PersonaBot Inbox without routing it into a Channel. The CLI diagnostic should expose Source Events, Admissions and Outbox/receiver state in addition to optional Channel projection. Native history capabilities are also conditional: Slack/Discord/Feishu qualified history paths cannot be assumed for WeChat/QQ, and history availability does not prove live default traffic delivery. Source: [CONTEXT](../../CONTEXT.md), [MessagingSnapshot](../../packages/core/src/messaging/outbound.ts), [history capability adapter](../../packages/core/src/messaging/dsh-im.ts).

Default traffic currently admits DMs and qualified mentions, with bounded automatic Conversation entries; non-mentioned group events do not enter default attention. Ordinary group text, threads, explicit routes and Conversation ingest remain separate choices. WeChat defaults are constrained to immediate DM behavior; platform-default settings currently validate Feishu/Slack/Discord/WeChat, excluding QQ. A five-platform CLI must not expose unsupported symmetric settings just because account registration supports all five. Source: [default traffic admission](../../packages/core/src/messaging/inbound.ts), [defaults schema](../../packages/core/src/messaging/defaults.ts), [root CONTEXT](../../CONTEXT.md).

Existing recorded real verification: P3 WeChat phone confirmation reached `ready` with `connected: true`; Feishu credential acceptance and the WeChat verification-code challenge were not exercised. That evidence does not qualify product Binding, external inbound admission or external reply. See [P3 evidence](../evidence/issue-1318/im-authorization-cli.md). This investigation performed no additional live tests.

## Options and Human decisions

These are proposals, not settled decisions or tickets.

1. **First observable outcome.** Prefer an already-authenticated test App → online PersonaBot creation → explicit Binding → verified receiver → one real external DM/mention → correlated reply, with CLI diagnostics at each point. This validates the common owner seams before adding three distinct native authorization adapters. If initial platform setup is the immediate user need, extend a single Provider setup path first instead.
2. **Five-platform authorization surface.** Prefer a Provider-owned capability descriptor and bounded public projection, with platform-specific credential shapes through stdin. Existing raw management RPCs can be adapted, but their receiver-mode transition and lifecycle semantics must be explicit. Decide whether Provider-first unification or per-platform CLI adapters should be the maintained public contract.
3. **What “can test without browser” promises.** Separate deterministic Host/Provider-fixture tests, live-model internal DM tests, real-platform receiving/sending tests, and UI/rendering tests. Decide which must be repeatable without Human participation and which may use documented phone/platform relay. A live model assertion should use stable observable milestones, not exact generated prose.
4. **Setup commands and partial completion.** Prefer composable commands and inspection/readback first; a convenience workflow may orchestrate them with stage receipts and resume. Decide whether failure keeps the native App, product Binding, and created PersonaBot for diagnosis or removes only explicitly owned disposable artifacts. Cross-owner account setup/Binding cannot be claimed atomic.
5. **Test destinations and receiver cutover.** Decide which isolated Apps/conversations each platform may use, whether existing accounts may be transferred, who provides phone/Portal steps, and what restoration behavior is required. This is a Human authorization/operating choice; source research cannot infer it.
