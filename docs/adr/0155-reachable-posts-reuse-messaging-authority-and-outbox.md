# Reachable posts reuse Messaging authority and Outbox

For [#1115](https://github.com/BotHarness/DeepSeekBot/issues/1115), an authenticated application may post to a group that its platform currently permits, without a saved Provider target or an inbound Source Event. The optional public Provider Service lists reachable groups and accepts a native conversation ID, authenticated fingerprint, cancellation signal and mandatory final beforeSend fence. It returns a checked native receipt. The compatible maintained Provider supports Lark, Discord and Slack discovery; accounts without that capability retain the saved-target path.

Application-defined Messaging remains the sole owner of Binding, blocks, conversation entries and Outbox. Client Profile sends and Bot tools use the same command. A first post creates a normal implicit conversation entry in the existing database after reachability and current ownership checks; it never invents an inbound Source Event or Inbox Admission. Blocked conversations cannot send. Muting or holding reception does not remove platform sending permission. A native permission read happens again before every new effect, and the final fence rechecks current Binding, entry and Provider registration.

The default loop guard is 60 proactive attempts per rolling hour per Binding, recorded through existing Outbox attempt facts. Human changes to the app limit are persisted on the Binding and increment its revision; null turns off the guard. Replies backed by a Source Event do not consume this allowance. Concurrent reservation happens in the owning transaction, and the final fence checks the reserved count again. Unknown attempts consume allowance because their effect may have occurred. No second quota store or scheduler is introduced.

Accepted, refused and unknown results retain their existing Outbox meaning. A stable request identity deduplicates repeated submissions. A proven preflight refusal is failed; an uncertain result after a native effect is unknown and is not retried on restart. Cancellation and revocation fence unstarted effects, while an already returned native receipt remains evidence of acceptance. Generation 77 adds the nullable application post-limit column, with forward repair or restoration of a pre-upgrade backup as the downgrade path.

Lark reachability uses native membership and moderation queries, including bounded speaking-list pagination for the Provider-verified Bot identity. Discord qualifies guild text and announcement channels using current membership, role overwrites and timeout state; thread discovery remains outside this capability. Slack lists joined public/private groups, reads current conversation membership and speaking restrictions, and requires authenticated read scopes plus chat:write; existing tokens need the additional read scopes before discovery is available. All adapters recheck native permission before posting and synchronously fence current authorization immediately before dispatch. The platform remains the authority for membership and permission. Historical inbound traffic and metadata alone never grant new sending authority.

The first Human-confirmed Lark group post was qualified at product 425bb709 and maintained Provider fbcfddd2. Later platform support and the Slack authorization-race fix have public-Service regressions; those checks do not establish native Discord, Slack or restricted Lark qualification.

Main integration retains its Generation 75 Self-Record and Generation 76 Memory commit migrations before the new Generation 77 post limit. Earlier unreleased QA branches used Generation 75 for post limits; that isolated Profile remains frozen as qualification evidence and must not be opened with this merged migration plan. Use a pre-feature backup or a separate QA Profile for the merged plan instead of interpreting the experimental generation as main history.
